# PROJECT: Offline Live Caption for iPhone

Act as a senior iOS software architect and developer.

I want you to design and incrementally develop a production-quality native iPhone application that generates real-time English closed captions from the iPhone microphone, with the primary requirement that transcription must work without an Internet connection.

The application is intended for situations such as conferences, training sessions, classes, meetings, and presentations where cellular/Wi-Fi connectivity may be poor or completely unavailable.

The project must be designed from the beginning with maintainability, privacy, accessibility, testing, documentation, and eventual Apple App Store distribution in mind.

Do not attempt to build the entire application at once.

Work incrementally according to the phases defined below.

At the end of every development phase:

1. The project must compile.
2. The implemented functionality must work.
3. Existing functionality must remain working.
4. Tests relevant to that phase must be executed.
5. Documentation must be updated.
6. Any architectural decisions must be documented.
7. Provide a short implementation summary.
8. Provide manual testing instructions.
9. Clearly identify what remains for the next phase.
10. Do not continue automatically to the next phase unless explicitly instructed.

---

# 1. PRODUCT VISION

Create a native iPhone application that allows a user to place the phone near a speaker during an English-language conference and read what is being said as live captions.

Primary workflow:

Speaker
↓
iPhone microphone
↓
On-device speech recognition
↓
Real-time English transcription
↓
Large readable captions
↓
Optional local transcript storage

The core transcription functionality must work offline.

Internet-based AI features may be introduced later, but they must always remain optional and separate from the offline transcription engine.

---

# 2. PRIMARY TECHNICAL APPROACH

Use Apple's native technologies whenever appropriate.

Preferred stack:

- Swift
- SwiftUI
- Apple Speech framework
- SpeechAnalyzer
- SpeechTranscriber
- AVFoundation / AVAudioEngine
- Swift Concurrency
- Observation or appropriate native state management
- SwiftData when persistent structured storage becomes necessary
- XCTest / Swift Testing where appropriate

Target modern iPhone versions that support the required on-device SpeechAnalyzer/SpeechTranscriber capabilities.

Do not use deprecated APIs when a current supported Apple API exists.

Before implementing a framework API, verify its current Apple documentation and availability requirements.

Do not silently replace the offline architecture with a cloud transcription service.

---

# 3. NON-NEGOTIABLE REQUIREMENTS

The core application must:

- Work without Internet connectivity.
- Capture audio using the iPhone microphone.
- Perform English speech-to-text on device.
- Display partial/live transcription with low perceived latency.
- Support long conference sessions.
- Remain responsive while transcribing.
- Handle interruptions and audio-session changes gracefully.
- Clearly indicate listening/transcribing state.
- Handle microphone permission correctly.
- Handle unavailable speech models/assets gracefully.
- Never require an OpenAI API key for offline transcription.
- Never embed secrets in the application.
- Avoid uploading conference audio unless a future feature explicitly requires it and the user knowingly opts in.
- Follow Apple's privacy and App Store requirements.

---

# 4. ARCHITECTURE

Use a clean, modular architecture.

Suggested initial modules/layers:

App
UI / Views
ViewModels
Services
Speech
Audio
Models
Persistence
Utilities

Avoid unnecessary abstraction during the MVP.

Prefer protocols where they provide real benefits such as testing or interchangeable implementations.

Important components may eventually include:

SpeechTranscriptionService
AudioCaptureService
TranscriptRepository
ConferenceSession
AppSettings
ConnectivityService
AIProcessingService

The offline speech engine must be isolated behind an abstraction so another engine, such as a local Whisper implementation, could be evaluated in the future without rewriting the UI.

Example conceptual protocol:

SpeechTranscribing

Possible implementations:

AppleSpeechTranscriber
FutureWhisperTranscriber

Do NOT implement Whisper during the initial phases.

---

# 5. DEVELOPMENT PRINCIPLE

Use vertical incremental development.

Every phase must produce a usable improvement.

Never create dozens of unfinished components for future phases.

Implement only what is required for the current phase while keeping the architecture extensible.

Keep the main branch/project buildable at all times.

Prefer simple working software over premature complexity.
